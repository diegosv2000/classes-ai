01El problema que resolvemos

Concurrencia

Los usuarios dan por hecho que su sistema puede hacer más de una tarea a la vez: seguir escribiendo en un procesador de textos mientras otras aplicaciones descargan archivos, manejan la cola de impresión y reproducen audio. E incluso esperan que una sola aplicación responda al mouse y teclado sin importar lo ocupada que esté modificando texto o actualizando la pantalla.

Ejemplo · un procesador de textos concurrente

proceso: editor de texto

responde al teclado revisa ortografía autoguardado actualiza pantalla
memoria compartida del proceso

Un software capaz de hacer esto es conocido como software concurrente. Cada tarea interna la soporta un hilo de ejecución.

02Las dos unidades de ejecución

Hilos y procesos

En la programación concurrente hay dos unidades básicas de ejecución. Un proceso tiene un entorno de ejecución autónomo: un conjunto completo y privado de recursos, en particular su propio espacio de memoria. Un hilo —también llamado proceso ligero— vive dentro de un proceso: crearlo requiere muchos menos recursos y comparte la memoria y archivos abiertos de su proceso.

ProcesoHilo
EntornoAutónomo y aisladoDentro de un proceso; cada proceso tiene al menos un hilo (el main thread)
RecursosConjunto completo y privado de recursos; propio espacio de memoriaComparte la memoria y archivos abiertos del proceso
ComunicaciónVía IPC del SO: pipes o sockets (funcionan incluso entre sistemas distintos)Directa leyendo/escribiendo memoria compartida: eficiente pero potencialmente problemática
Costo de creaciónAltoBajo (proceso ligero)

Desde el punto de vista del programador, toda aplicación arranca con un único hilo — el main thread — que tiene la capacidad de crear hilos adicionales. La memoria compartida es el superpoder y la maldición de los hilos: comunicación eficiente, pero si dos hilos coordinan mal, aparecen las condiciones de carrera (semana 5).

03Hardware

Hilos y CPUs

Un thread o hilo de ejecución es la ejecución secuencial de una serie de instrucciones dentro de un programa. La mayoría de lenguajes son single-threaded por defecto, pero el hardware evolucionó: el concepto de thread llegó a la CPU con el multinúcleo. Compara los dos escenarios:

Múltiples hilos · múltiples CPUs

Cada hilo tiene su propio núcleo: avanzan de verdad al mismo tiempo.

Todos comparten el mismo núcleo: el SO los va turnando muy rápido.

Los sistemas operativos ocultan estos detalles: el usuario no distingue si corre en un núcleo o en varios. Piensas en "hilos" y el SO decide cómo y dónde ejecutarlos.

04La plataforma Java

Multi-threading en la plataforma Java

Cada aplicación Java arranca con un thread llamado thread principal (main thread). Este thread tiene la habilidad de crear threads adicionales. Es la base de todo lo que haremos en el curso.

aplicación java

main thread (existe al arrancar) hilo creado por main hilo creado por main
objetos compartidos: acceso desde todos los hilos

Pero la programación multi-threaded es más compleja que la secuencial, por dos razones:

  • Acceso compartido de objetos: varios hilos tocan los mismos datos.
  • Riesgo de condición de carrera: el resultado depende del entrelazado de los hilos (lo verás en acción la semana 5).

05Ciclo de vida

Estados de un thread

Según el material, un thread puede estar en uno de estos cinco estados — observa el ciclo que recorre la ilustración:

Runningen curso de ejecución, con el control de la CPU
Runnableready to run: puede ejecutarse pero no se le ha dado la orden
Blockedesperando por algún recurso o que ocurra un evento
Suspendedvoluntariamente permite que otros threads se ejecuten
Resumedready to run después de haber estado suspendido o bloqueado
Terminatedsu run() terminó: fin del hilo
Ciclo: Runnable → Running → (Blocked | Suspended) → Resumed → Runnable → … → Terminated

Estos nombres vienen del modelo conceptual del material. Java moderno, en su enum Thread.State, define: NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING y TERMINATED. Las ideas de fondo — listo, en ejecución, esperando un recurso — son las mismas; ten presente que los nombres exactos difieren.

06Reparto de la CPU

Prioridades de un thread

Las prioridades determinan qué thread recibe el control de la CPU y consigue ser ejecutado primero. En Java se definen con un entero del 1 al 10: a mayor valor, mayor la oportunidad de ser ejecutado primero. La clase Thread define tres constantes:

La prioridad por defecto de un hilo es 5 (NORM_PRIORITY). Se lee y escribe con getPriority() y setPriority(int).

Cuidado: las prioridades son una sugerencia, no una garantía. Depende de la JVM y de cómo el sistema operativo decida planificar los hilos. Y si dos threads tienen la misma prioridad, la ejecución depende del sistema operativo.

07Forma 1 de 2

Crear un hilo: implementar Runnable

Cada hilo en Java se asocia con una instancia de la clase Thread. La primera forma de definir el trabajo del hilo es proporcionar un objeto Runnable: la interfaz Runnable define un único método, run, que contiene el código a ejecutarse en el hilo.

public class HelloRunnable implements Runnable { public void run() { System.out.println("Hello from a thread!"); } public static void main(String args[]) { (new Thread(new HelloRunnable())).start(); } }

Se crea un Thread pasándole el Runnable como argumento, y se lanza con start().

Por qué funciona: la clase Thread ya implementa Runnable — un Thread es, a la vez, una tarea ejecutable.

08Forma 2 de 2

Crear un hilo: extender Thread

La segunda forma es crear una subclase de Thread. La clase Thread implementa por sí misma la interfaz Runnable, aunque su método run no hace nada — por eso lo sobrescribes:

public class HelloThread extends Thread { public void run() { System.out.println("Hello from a thread!"); } public static void main(String args[]) { (new HelloThread()).start(); } }

Aquí no necesitas un objeto aparte: la propia instancia es el hilo y la tarea.

En ambas formas el código del hilo vive en run(). La diferencia está en dónde defines ese método y qué le pasas al constructor.

09¿Cuál usar?

Runnable vs extender Thread

Ambas formas logran lo mismo, pero el material deja estas observaciones importantes:

Ambas requieren start()

En los dos casos se debe invocar Thread.start() para iniciar el nuevo hilo. Olvidarlo es el error más común: el hilo nunca corre.

Runnable necesita un Thread

Al usar la interfaz Runnable es necesario crear una instancia de la clase Thread entregando el objeto Runnable como argumento.

Runnable es más general

Podemos crear una subclase de cualquier clase que no sea Thread e igualmente implementar Runnable. No gasta la única herencia disponible en Java.

Extender Thread es cómodo… y limita

Facilita el trabajo en aplicaciones simples, pero nos limita a tener que usar una clase descendiente de Thread.

Regla práctica para el curso: prefiere Runnable salvo que tengas una razón puntual para extender Thread.

10Métodos esenciales · 1 de 3

Thread.currentThread()

Es un método estático que retorna una referencia al objeto Thread que se está ejecutando actualmente — útil para saber quién eres y pasar tu propio hilo como argumento:

public class ThreadDemo implements Runnable { ThreadDemo() { // main thread Thread currThread = Thread.currentThread(); Thread t = new Thread(this, "Admin Thread"); System.out.println("current thread = " + currThread); System.out.println("thread created = " + t); t.start(); } public void run() { System.out.println("This is run() method"); } public static void main(String args[]) { new ThreadDemo(); } }

Fíjate en el constructor: currentThread() devuelve el main thread (quien está ejecutando ese código), mientras que t es el hilo nuevo creado con nombre "Admin Thread" — aún no empieza hasta start().

11Métodos esenciales · 2 de 3

Thread.sleep()

Provoca que el hilo actual suspenda su ejecución por un periodo de tiempo especificado (en milisegundos):

public class SleepMessages { public static void main(String args[]) throws InterruptedException { String importantInfo[] = { "Mares eat oats", "Does eat oats", "Little lambs eat ivy" }; for (int i = 0; i < importantInfo.length; i++) { // Pause for 4 seconds Thread.sleep(4000); System.out.println(importantInfo[i]); } } }

Tres advertencias importantes del material:

  • No se garantizan tiempos precisos: los descansos están limitados por las facilidades del sistema operativo subyacente.
  • El periodo puede ser detenido por interrupciones: no asumas que sleep suspende exactamente el tiempo indicado.
  • InterruptedException se lanza cuando otro hilo interrumpe al hilo actual mientras sleep está activo — por eso main la declara con throws.

12Cooperación entre hilos

Interrupciones

Una interrupción es una indicación a un hilo de que debe detenerse y hacer algo más. Un hilo envía la interrupción invocando interrupt() sobre el objeto Thread a interrumpir. Es un mecanismo cooperativo: el hilo debe ser capaz de manejar su propia interrupción, y decide el programador qué hace — lo más común es que termine.

hilo trabajador · ejecutando
run(): trabajando…

Pulsa interrupt() y observa: el hilo no muere de golpe — en su siguiente chequeo de interrupción decide terminar limpiamente. Así funciona la interrupción cooperativa.

13Interrupciones · manejo

Manejando interrupciones

La forma de manejar una interrupción depende de qué esté haciendo el hilo en ese momento. Si el hilo invoca con frecuencia métodos que arrojan InterruptedException, lo usual es simplemente retornar del método run() tras atrapar la excepción:

Caso 1 · el hilo duerme (sleep)

for (int i = 0; i < importantInfo.length; i++) { // Pause for 4 seconds try { Thread.sleep(4000); } catch (InterruptedException e) { // We've been interrupted: // no more messages. return; } // Print a message System.out.println(importantInfo[i]); }

Caso 2 · el hilo no usa métodos que lancen la excepción

for (int i = 0; i < inputs.length; i++) { heavyCrunch(inputs[i]); if (Thread.interrupted()) { // We've been interrupted: // no more crunching. return; } } // En aplicaciones más complejas, // tiene más sentido propagarla: if (Thread.interrupted()) { throw new InterruptedException(); }

En el caso 2, el hilo hace trabajo pesado (sin sleep) y chequea periódicamente Thread.interrupted(): retorna true si se ha recibido una interrupción. En aplicaciones más complejas conviene arrojar un InterruptedException al detectarla, para que el código superior la trate de forma uniforme.

14Interrupciones · el mecanismo interno

La bandera Interrupt Status

El mecanismo de interrupción se implementa con una bandera interna conocida como Interrupt Status. Cada método interactúa con ella de forma distinta — esta tabla es la clave para no confundirlos nunca:

MétodoQué hace con la bandera
Thread.interrupt()Establece la bandera del hilo objetivo: le pide que se detenga y haga algo más.
Thread.interrupted() (estático)El hilo actual verifica si fue interrumpido y, al hacerlo, limpia la bandera.
isInterrupted() (de instancia)Un hilo verifica el estado de otro hilo sin modificar la bandera.

Por convención, cualquier método que termine lanzando una InterruptedException limpia el Interrupt Status al hacerlo — por eso tras atrapar la excepción la bandera ya no está activa.

15Métodos esenciales · 3 de 3

join(): esperar a otro hilo

El método join() permite a un hilo esperar por la terminación de otro. Si t es un objeto Thread cuyo hilo está en ejecución, t.join() ocasiona que el hilo actual pause su ejecución hasta que el hilo de t termine:

main thread

t.start();
trabajo propio…
t.join(); // se detiene aquí
continúa cuando t termina

hilo t

run(): trabajando…
…
termina → main se despierta

  • El uso adecuado de join() permite especificar un periodo de espera (no esperar indefinidamente).
  • Al igual que sleep(), join() responde a una interrupción saliendo con una InterruptedException.

¿Cuándo usarlo? Cuando el hilo principal necesita el resultado de los hilos trabajadores antes de continuar: lanzas los hilos, haces tu parte, y con join() esperas a que todos terminen.

16Hilos de servicio

Daemon threads

Un Daemon Thread en Java es un hilo que proporciona servicios a los hilos de usuario. La regla que los define: cuando todos los hilos de usuario terminan, la JVM termina los daemon threads automáticamente — nadie espera a los daemons. El ejemplo clásico es el garbage collector.

Métodos

  • setDaemon(boolean status): marca el hilo como daemon o user thread.
  • isDaemon(): verifica si el hilo es un daemon thread.

Ejemplo

TestDaemonThread1 t1 = new TestDaemonThread1(); t1.setDaemon(true); // t1 es daemon t1.start(); t2.start(); t3.start(); // user threads // run(): if (Thread.currentThread().isDaemon()) System.out.println("daemon thread work"); else System.out.println("user thread work");

Regla crítica

// t1 YA fue iniciado: t1.start(); t1.setDaemon(true); // throws IllegalThreadStateException

Si quieres establecer un user thread como daemon, debe hacerse antes de iniciarlo; de lo contrario arrojará un IllegalThreadStateException.

Nota: el material describe a los daemons como hilos de baja prioridad. En Java, la condición de daemon y la prioridad son propiedades independientes — un daemon puede tener prioridad 10. La esencia está en su ciclo de vida: viven para servir y mueren cuando los user threads terminan.

Resumen de la semana: ya sabes qué es un hilo, cómo crearlo (Runnable o extendiendo Thread), controlarlo (sleep, join, prioridades) y detenerlo limpiamente (interrupciones). Con esto puedes escribir tu primer programa multihilo en Java.
