01El punto de partida

El problema de compartir memoria

Los hilos se comunican principalmente compartiendo el acceso a campos y objetos referenciados. Esta forma de comunicación es extremadamente eficiente, pero conlleva dos posibles errores:

Interferencia de hilos

Dos operaciones sobre la misma data se entrelazan y una pisa el resultado de la otra.

Errores de consistencia de memoria

Diferentes hilos tienen una vista inconsistente de lo que debería ser la misma data.

Para prevenir estos errores existe la sincronización. Pero cuidado: la sincronización puede introducir problemas de contención de hilos (ej. starvation y livelock), que ocurren cuando 2 o más hilos intentan acceder a un mismo recurso simultáneamente — el runtime ejecuta uno o más hilos más lento, o incluso los suspende. Todo esto es la semana.

02w5_1 · el error fundamental

Interferencia de hilos

Ocurre cuando dos o más operaciones en hilos distintos, actuando sobre la misma data, se entrelazan: ambas constan de múltiples pasos y sus secuencias se sobreponen. Con c++ descompuesto en sus 3 pasos (recuperar, incrementar, almacenar), la secuencia del material:

Hilo Ac++
c = 0
memoria compartida
Hilo Bc--
Recorrido automático del entrelazado…

El resultado del hilo A se pierde al ser sobrescrito por el hilo B. Ejemplo completo del material: la clase Counter con increment(), decrement() y value() — sin sincronizar, es vulnerable.

03w5_1 · la vista de los datos

Consistencia de memoria y happens-before

Los errores de consistencia de memoria ocurren cuando diferentes hilos tienen una vista inconsistente de lo que debería ser la misma data. Ejemplo del material: counter = 0 compartido; el hilo A imprime y el hilo B incrementa — el valor impreso podría ser 0 o 1, porque no hay garantía de visibilidad sin una relación happens-before.

La relación happens-before es simplemente una garantía de que las escrituras de memoria de una sentencia son visibles para otra sentencia. Dos sentencias que la crean:

Thread.start()

Toda sentencia que guarde happens-before con esta llamada también lo guardará con cada sentencia ejecutada en el hilo creado.

Thread.join()

Todas las sentencias ejecutadas por el hilo terminado tienen happens-before con toda sentencia que siga a un join() exitoso.

Si una acción A happens-before una acción B, entonces los efectos de A son visibles para B. Otras relaciones las verás con synchronized, volatile y los locks.

04w5_1 · la primera herramienta

Métodos sincronizados

Para crear uno basta incluir la palabra clave synchronized en su declaración. Es la solución al Counter de la slide anterior:

public class SynchronizedCounter { private int c = 0; public synchronized void increment() { c++; } public synchronized void decrement() { c--; } public synchronized int value() { return c; } }

Efecto 1 · no se interponen

No es posible que dos invocaciones de métodos sincronizados sobre el mismo objeto se interpongan: mientras un hilo ejecuta uno, los demás hilos que hayan invocado métodos sincronizados del mismo objeto se bloquean hasta que el primero termine.

Efecto 2 · happens-before automático

Cuando un método sincronizado termina, automáticamente establece una relación happens-before con cualquier invocación subsecuente de un método sincronizado para el mismo objeto.

05w5_1 · el mecanismo interno

Bloqueo intrínseco (monitor)

La sincronización se construye alrededor de una entidad interna conocida como bloqueo intrínseco o monitor de bloqueo (a veces simplemente "monitor"). Cada objeto tiene uno asociado:

hilo A · posee el bloqueo hilo B · espera hilo C · espera
  • Un hilo que necesite acceso exclusivo y consistente a los campos de un objeto debe adquirir el bloqueo intrínseco del objeto y liberarlo cuando termine.
  • Mientras un hilo lo posea, ningún otro hilo podrá adquirir el mismo bloqueo.
  • Liberar el bloqueo establece una relación happens-before entre esa acción y cualquier adquisición subsecuente del mismo bloqueo.

Esto explica los dos efectos de la slide anterior: "métodos sincronizados del mismo objeto" significa "compiten por el mismo bloqueo intrínseco".

06w5_1 · sincronización fina

Sentencias sincronizadas y reentrancia

A diferencia de los métodos sincronizados, las sentencias sincronizadas deben especificar el objeto que proporciona el bloqueo intrínseco — y permiten sincronizar solo un bloque, no todo el método:

public void addName(String name) { synchronized(this) { lastName = name; nameCount++; } nameList.add(name); // fuera de la sección crítica }

Sincronización reentrante: un hilo no puede adquirir un bloqueo en posesión de otro hilo, pero sí puede adquirir un bloqueo que ya tenga. Permitir que un hilo adquiera el mismo bloqueo más de una vez habilita la sincronización reentrante: un código sincronizado puede invocar otro método sincronizado, y ambos usan el mismo bloqueo. Gracias a ello no es necesario tomar precauciones para evitar que un hilo se bloquee a sí mismo.

Y sobre acceso atómico: una acción atómica ocurre una a la vez, siempre se completa del todo o no sucede, y ningún efecto secundario es visible hasta completarse. Toda lectura y escritura es atómica para variables volatile, y cualquier escritura a una variable volatile establece happens-before con las lecturas subsecuentes de esa variable.

07w5_2 · la abstracción

Monitores

Un monitor es un mecanismo de sincronización que controla el acceso de múltiples hilos a recursos compartidos, garantizando que solo un hilo ejecute un bloque de código crítico a la vez. En Java, cada objeto puede actuar como monitor:

Implementación en Java

  • Cada objeto tiene un monitor implícito.
  • Se accede mediante synchronized en métodos o bloques.
  • Solo un hilo puede poseer el bloqueo del monitor en un momento dado.

El ejemplo del material

class Contador { private int valor = 0; public synchronized void incrementar() { valor++; } public synchronized int obtenerValor() { return valor; } } // 2 HiloIncrementador (1000 c/u) + join() // → Valor final: 2000, siempre

El programa del material une todo lo de la semana 1: dos hilos que incrementan 1000 veces cada uno, join() para esperarlos, y el monitor (synchronized) garantizando el resultado.

08w5_2 · el error sin sincronización

Condición de carrera

Ocurre cuando dos o más hilos acceden y modifican un recurso compartido al mismo tiempo, sin la debida sincronización. El resultado final depende del orden en que se ejecuten las instrucciones de los hilos — lo cual es no determinista.

En Java suele pasar cuando varios hilos modifican una variable compartida sin usar synchronized. El experimento del material: dos hilos, 1000 incrementos cada uno.

esperado

2000

obtenido

1987 · 1995…

¿Por qué? La operación valor++ no es atómica: internamente se descompone en leer, incrementar y escribir, y los hilos pueden interrumpirse entre esos pasos.

① leer ② incrementar ③ escribir

Solución: el monitor con synchronized — solo un hilo ejecuta el método a la vez, y el resultado será siempre 2000.

09w5_2 · liveness roto I

Deadlock

Dos o más hilos quedan bloqueados para siempre, esperando recursos que nunca se liberan. Cada hilo posee un recurso y espera otro que está en manos del otro; como ninguno libera lo que tiene, ambos quedan bloqueados indefinidamente.

Hilo 1

posee Recurso A

espera Recurso B

Hilo 2

posee Recurso B

espera Recurso A

El ejemplo del material (los amigos que se inclinan): cada Tarea hace synchronized(recurso1) y luego synchronized(recurso2) — pero t1 las toma en orden (A, B) y t2 en orden inverso (B, A). El método bow adquiere el bloqueo del amigo que saluda y bowBack necesita el bloqueo del otro: ambos se bloquean para siempre.

Cómo evitarlo — tres recetas del material:

  • Orden consistente: adquirir siempre los recursos en el mismo orden.
  • Tiempo de espera: bloqueos con timeout (tryLock en ReentrantLock).
  • Diseño cuidadoso: minimizar la necesidad de múltiples bloqueos.

10w5_2 · liveness roto II

Livelock

Dos o más hilos no están bloqueados, pero siguen cambiando de estado en respuesta a las acciones del otro, sin avanzar nunca en su trabajo. A diferencia del deadlock (hilos bloqueados esperando recursos), aquí los hilos están activos, atrapados en un ciclo de reacciones inútiles.

La analogía del material: dos personas en un pasillo estrecho — una se mueve a la izquierda, la otra a la derecha; siguen bloqueándose mutuamente y nadie pasa.

Trabajador 1 · cede el recurso… Trabajador 2 · cede el recurso…

En el ejemplo del código: cada trabajador intenta intentarUsar() el primer recurso; si no logra el segundo, libera el primero y reintenta — como ambos hacen lo mismo, pueden quedarse cediendo y retomando sin progresar indefinidamente.

El livelock es más difícil de detectar que el deadlock porque los hilos parecen activos. La solución suele ser introducir esperas aleatorias o reglas claras de prioridad para que los hilos no cedan indefinidamente.

11w5_2 · liveness roto III

Starvation (inanición)

Ocurre cuando un hilo es incapaz de ganar acceso regular a recursos compartidos y no puede hacer progresos. El hilo sigue vivo, pero no progresa porque siempre queda esperando.

hilo codicioso hilo codicioso hilo afectado · nunca entra

Sucede cuando los recursos compartidos son inaccesibles por largos periodos debido a hilos codiciosos — por ejemplo, cuando se usan prioridades de hilos o cuando el sistema de bloqueo favorece constantemente a ciertos hilos.

La starvation es un problema de equidad, no de bloqueo total (como el deadlock). Se mitiga con políticas de planificación más justas — fair locks (ReentrantLock con opción de equidad) — o evitando el uso excesivo de prioridades.

12w5_2 · las garantías

Mutex (mutua exclusión) y thread-safe

Mutex

Solo un hilo puede acceder a un recurso compartido en un momento dado. En Java se logra con synchronized, que convierte un método o bloque en una sección crítica. Es la base de la programación concurrente segura: con ella, el resultado del contador es siempre 2000; sin ella, los hilos se pisan y queda menor (condición de carrera).

Thread-safe

Un código puede ser ejecutado por múltiples hilos al mismo tiempo sin producir resultados incorrectos ni condiciones de carrera. En Java se logra con:

  • Bloqueo intrínseco con synchronized.
  • Variables volatile para asegurar visibilidad.
  • Clases de java.util.concurrent (AtomicInteger, ConcurrentHashMap…).

La idea central: los datos compartidos deben estar protegidos y mantener siempre la consistencia. Es esencial cuando varios hilos comparten y modifican datos.

13w5_2 · acceso múltiple

Semaphore

Mecanismo de sincronización que controla el acceso a uno o más recursos mediante un contador. A diferencia del mutex (que permite solo 1 acceso), el semáforo permite n accesos simultáneos. La analogía del material: un estacionamiento con 3 espacios — cada auto que entra adquiere un permiso, cada auto que sale lo libera, y si no hay espacios, se espera.

espacio 1
espacio 2
espacio 3

Semaphore parking = new Semaphore(3); // 10 hilos "Auto" intentan parking.acquire(); // bloquea si no hay permisos disponibles // … estaciona, duerme 2s … parking.release(); // libera el permiso parking.availablePermits() // espacios restantes

14w5_2 · la propiedad global

Liveness

Liveness (capacidad de "seguir vivo") es la propiedad de un sistema concurrente que garantiza que los hilos siempre progresan hacia su objetivo, sin quedarse atascados indefinidamente. Los tres enemigos del liveness que ya conoces:

Deadlock

Hilos bloqueados permanentemente, cada uno esperando un recurso del otro.

Starvation

Un hilo nunca obtiene acceso al recurso compartido: falta de equidad.

Livelock

Hilos activos pero sin progreso: respondiéndose entre sí en un ciclo inútil.

Al diseñar secciones críticas, piensa en liveness: resolver la condición de carrera (deadlock posible) o la contención (starvation/livelock posible) — la sincronización correcta es la que protege los datos y deja que todos progresen.

15Comunicación entre hilos

wait(), notify() y notifyAll()

La comunicación entre hilos permite que un hilo se pause durante una sección crítica y otro pueda entrar. Se implementa con tres métodos de la clase Object:

  • wait(): el hilo libera el bloqueo del objeto y queda en espera, hasta que otro invoque notify()/notifyAll() o transcurra un tiempo.
  • notify(): despierta uno de los hilos esperando (elección arbitraria de la JVM).
  • notifyAll(): despierta todos los hilos esperando.

Regla de oro

Solo pueden llamarse dentro de un método o bloque synchronized, porque dependen del monitor del objeto: el hilo debe ser dueño del monitor. Si no lo es, se arroja IllegalMonitorStateException.

Tras despertar

El hilo despertado no puede proceder hasta que el hilo actual libere el bloqueo; los despertados no tienen privilegios ni desventajas por el bloqueo.

Patrón del material: el consumidor hace while(!disponible) wait(); y el productor marca disponible = true y llama notify(). Pruébalo con tres consumidores esperando:

Con notify() solo uno despierta y consume; los demás siguen en wait(). Con notifyAll() todos despiertan y compiten: uno consume y los demás vuelven a esperar.

15bComunicación entre hilos · decisión

¿notify() o notifyAll()?

La diferencia está en cuántos hilos en espera son despertados al invocarlo sobre un objeto sincronizado:

notify() · uno

  • Despierta solo un hilo esperando en el monitor.
  • No se puede controlar cuál: la elección depende de la JVM.
  • Útil cuando basta con que un único consumidor continúe.

notifyAll() · todos

  • Despierta todos los hilos esperando.
  • Cada hilo luego competirá por adquirir el bloqueo y continuar.
  • Útil cuando hay varios consumidores y quieres darles la oportunidad de reaccionar.

Comportamiento del ejemplo del material (3 consumidores, 1 recurso):

  • Con notify(): uno consume; los demás siguen esperando.
  • Con notifyAll(): todos despiertan, pero solo uno logra consumir (el recurso se marca no disponible) — los otros vuelven a esperar.

En resumen: notify() cuando basta uno; notifyAll() cuando hay varios esperando y quieres darles la oportunidad de competir.

16w5_1 · locks explícitos

Lock: bloqueos más extensivos

Las interfaces Lock (paquete java.util.concurrent.locks) proporcionan operaciones de bloqueo más extensivas que los métodos sincronizados: estructuración más flexible, distintas propiedades y soporte de múltiples objetos Condition:

Lock l = ...; l.lock(); try { // access the resource protected by this lock } finally { l.unlock(); }

Lock vs synchronized: los métodos sincronizados fuerzan adquisiciones y liberaciones estructuradas por bloques (con múltiples bloqueos, se liberan en orden opuesto y en el mismo scope). Los Locks permiten adquirir y liberar en cualquier orden e incluso en distintos scopes, y añaden: intentar adquirir sin bloquearse (tryLock) y adquisiciones interrumpibles.

Regla de oro: si el bloqueo y desbloqueo ocurren en distintos scopes, todo el código ejecutado durante el bloqueo debe ir en try-finally para garantizar la liberación.

Métodos de Lock y Condition

Condition

Permite que un hilo suspenda su ejecución hasta ser notificado de que alguna condición de estado podría ya no ser verdadera. Reemplaza al monitor con wait/notify/notifyAll, igual que Lock reemplaza a synchronized:

await()espera hasta ser "señalado" o interrumpido

Como el acceso al estado compartido ocurre en distintos hilos, debe estar protegido: la condición está asociada a un bloqueo — se obtiene con newCondition() del Lock.

17w5_3 · visibilidad

volatile

Palabra clave para variables compartidas entre múltiples hilos: indica que la variable no debe ser cacheada por los hilos en registros o memoria local — siempre se lee y escribe desde la memoria principal.

Volatile asegura

  • Visibilidad de cambios: todos los hilos leen el valor actualizado.
  • Uso típico: banderas de control, estados de ejecución, variables que cambian de forma simple (true/false, referencias).

Ejemplo conceptual: un hilo corre en bucle hasta que una variable cambie a false. Sin volatile podría seguir corriendo por siempre con una copia vieja; con volatile detecta el cambio inmediatamente y se detiene.

Volatile NO hace

  • No asegura atomicidad: no evita condiciones de carrera en operaciones compuestas (contador++).
  • No es sincronización completa.
  • No reemplaza mecanismos más complejos: para operaciones seguras se necesita synchronized o clases como AtomicInteger.

Combinación del material: volatile + synchronized juntos — volatile asegura la visibilidad inmediata; synchronized asegura la atomicidad y exclusión mutua en las operaciones compuestas.

17aw5_3 · operaciones atómicas

AtomicInteger

Clase de java.util.concurrent.atomic que permite realizar operaciones sobre enteros de manera atómica (segura en concurrencia). A diferencia de volatile o variables normales, asegura que incrementAndGet() o addAndGet() no se solapen entre hilos. Muy usada cuando varios hilos modifican un contador o estado compartido.

Métodos principales

get() / set(v)leer / escribir el valor
getAndSet(v)devuelve el actual y luego lo reemplaza
incrementAndGet()incrementa en 1 y devuelve el nuevo
getAndIncrement()devuelve el actual y luego incrementa
decrementAndGet() / getAndDecrement()decremento (antes/después)
addAndGet(d) / getAndAdd(d)suma un delta (antes/después)

Sincronización sin bloqueos

compareAndSet(expect, update)cambia el valor solo si coincide con el esperado; true si lo logra
weakCompareAndSet(e, u)similar, pero puede fallar espuriamente (más rápido)
class ContadorAtomic { private AtomicInteger valor = new AtomicInteger(0); public void incrementar() { valor.incrementAndGet(); // atómico } }

Con el ejemplo del material (2 hilos × 1000 incrementos): el valor esperado es 2000 y el real también — sin synchronized y sin bloqueos.

18w5_3 · colas bloqueantes

BlockingQueue y ArrayBlockingQueue

BlockingQueue es una interfaz que define el comportamiento de una cola bloqueante: no se puede instanciar directamente, pero permite programar contra la abstracción y cambiar de implementación (ArrayBlockingQueue, LinkedBlockingQueue…) sin tocar el resto del código. ArrayBlockingQueue es la clase concreta: usa un array circular fijo cuya capacidad se define al crearla y no cambia.

productor · put()

cola (capacidad fija)

put bloquea si está llena · take bloquea si está vacía

consumidor · take()

El ejemplo del material: una cola de capacidad 2 recibe 3 valores — el tercero bloquea al productor hasta que el consumidor saque uno. Cada consumidor procesa lo extraído (suma de cuadrados, factorial). Ambas reglas: bloquean al productor si se excede la capacidad, y al consumidor si la cola está vacía.

BlockingQueue = abstracción flexible; ArrayBlockingQueue = implementación concreta acotada y eficiente. El patrón productor-consumidor, resuelto por la librería — sin wait/notify a mano.

19w5_3 · tareas con resultado

Callable, Future y FutureTask

ClaseQué esUso diferenciado
Callable<V> Interfaz similar a Runnable, pero su método call() devuelve un resultado y puede lanzar excepciones Definir la lógica de la tarea con retorno
Future<V> Representa el resultado de una tarea asíncrona: isDone() consulta si terminó, cancel() la cancela, get() obtiene el resultado (bloqueando hasta que exista) Manejar resultados asíncronos: esperar o consultar estado
FutureTask<V> Clase concreta que implementa Runnable y Future: envuelve un Callable o Runnable y se ejecuta en un hilo directo (new Thread(task).start()) o en un ExecutorService Control total: ejecución y resultado en un solo objeto
ExecutorService executor = Executors.newFixedThreadPool(2); Callable<Integer> suma = ...; // 1. definir la tarea (1+2+…+5) Future<Integer> f = executor.submit(suma); // 2. enviarla al executor System.out.println(f.get()); // 3. obtener el resultado (bloquea) FutureTask<Integer> task = new FutureTask<>(factorialCallable); new Thread(task).start(); // FutureTask en un hilo directo System.out.println(task.get()); // 5! = 120

El flujo del ejemplo del material: Callable define la tarea → Future recibe el resultado del executor → FutureTask combina ejecución y resultado — ambos terminan con get() y el executor se cierra con shutdown().

20w5_3 · gestión de hilos

ThreadPool y Executors

Un ThreadPool es un conjunto de hilos que ejecutan tareas. Puede ser útil tener más de un pool por tres razones del material:

Separación de responsabilidades

un pool para cálculo intensivo y otro para E/S

Control de recursos

evitar que tareas pesadas bloqueen a las ligeras

Priorización

tamaños de pool distintos según importancia

Executors es la fábrica que crea los distintos tipos de ExecutorService — en lugar de crear hilos a mano con new Thread(...), simplifica y controla la concurrencia:

newFixedThreadPool(n)

pool con n hilos fijos

newCachedThreadPool()

pool dinámico que ajusta el número de hilos según la carga

newSingleThreadExecutor()

un solo hilo: tareas en orden

El ejemplo del material encadena dos executors: el Executor1 calcula algo sencillo y guarda el resultado en una variable compartida; se espera su terminación; y el Executor2 usa ese resultado para un cálculo pesado — cada uno independiente, pero encadenados en secuencia. Los pools se cierran con shutdown() (y awaitTermination para esperarlos).

20aw5_3 · tareas programadas

ScheduledExecutorService

Extensión de ExecutorService que permite programar tareas para que se ejecuten después de un retraso o de forma periódica. Muy útil para temporizadores, tareas repetitivas o procesos que deben ejecutarse cada cierto intervalo. Se crea con Executors.newScheduledThreadPool(n):

MétodoComportamiento
schedule(task, delay, unit)ejecuta una tarea una vez después de un retraso
scheduleAtFixedRate(task, initDelay, period, unit)ejecuta periódicamente con intervalo fijo (el período cuenta desde el inicio de la tarea anterior)
scheduleWithFixedDelay(task, initDelay, delay, unit)periódica, pero el tiempo se cuenta desde que terminó la tarea anterior
ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(3); scheduler.schedule(tarea1, 2, TimeUnit.SECONDS); // una vez, tras 2s scheduler.scheduleAtFixedRate(tarea2, 1, 3, TimeUnit.SECONDS); // cada 3s

Diferencia fina entre las dos periódicas: AtFixedRate mantiene la cadencia (cada 3s, sin importar cuánto dure la tarea); WithFixedDelay respeta el descanso entre el fin de una tarea y el inicio de la siguiente.
